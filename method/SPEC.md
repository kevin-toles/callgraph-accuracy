# Call-graph review spec

You are checking a static call-graph tool's output against real source code. Judge each edge against THIS spec, not against what you think the ideal tool would do. If the spec does not cover a case, say "spec gap" and describe it — do not count it as a tool error.

## Edge fields
`caller_id, callee_id, call_type (direct|method|constructor|callback|macro|implicit), source_file (absolute), line_number, confidence (high|medium|low|unknown)`; `is_async` / `is_external` appear only when true.
- `macro`: a macro invocation (C/C++/ObjC function-like macros, Rust `name!`). Calls written inside macro arguments are separate ordinary edges.
- `implicit`: an execution edge the language runs without a written call — `Type#<clinit>` → `Type#field` (static initializer), `Type#<init>` → `Type#field` (instance field initializer). Line = the field's line.

## ID format (all languages)
- Method: `Type#member`. Nested types are dotted: `Outer.Inner#m`. Some languages prefix a module/package qualifier with dots (see per-language notes).
- Constructor / initializer call: `Type#<init>`.
- Free function: its name (with the language's module qualifier where it has one).
- Call on a receiver of **unknown type**: `recv.member`, using the LAST receiver segment (`self.client.get()` → `client.get`; `a.b.c()` → `b.c`).
- Call on a **computed receiver** (call result, index, literal, `super` when the superclass is not in the scan): `.member` — a leading dot means "receiver unknown".
- `self.m()` / `this.m()` / a bare call to a member of the enclosing type → `Type#m`. If `m` is defined only on a superclass that is in the scan, the callee is `Superclass#m`.
- A local bound directly to a function literal (`const f = () => …`, `local function f`, `let f x = …`, `where f = …`, local `fun`/`def`/`func`, a Rust `fn` item inside a function body, a PHP `$f = function`/`fn`, a C++ `auto f = [..]`, a Kotlin `val f = { }`) is a **named nested function**: ID `outer.f` (Python form), and calls to it are high. Anonymous functions, lambdas, object-literal methods and anonymous-class members fold into the nearest enclosing named function (or the module/type at top level). A caller is never empty.
- Call through a parameter, local variable or stored property holding a function (callback, closure, fn pointer, delegate) → callee is the variable's name, `call_type` callback, confidence unknown.
- Each call in a multi-line method chain is reported on the line of its own method name, not the chain's first line.

- Code outside a method body: the caller is its location. Field/val initializer → `Type#field`; C# property accessor → `Type#Prop` (get) / `Type#Prop=` (set); Ruby setter → `Type#x=`; `static {}` block → `Type#<clinit>`. Non-lazy initializers also get an `implicit` edge from `<clinit>`/`<init>`; lazy ones do not.
- Superclass constructor calls (`super(...)`, `: base(...)`, `: this(...)`, PHP `parent::__construct(...)`, Ruby `super` inside `initialize`) → `Parent#<init>`, constructor. A Ruby `initialize` / PHP `__construct` definition's ID is `Type#<init>`.
- Anonymous subclass instantiation (`new Iface() {…}`, Scala `new Trait {…}`): no constructor edge when the named type is an interface/trait (it has no constructor); when it is a class (including abstract), `Type#<init>`, constructor, as usual. Calls inside the body fold into the enclosing function as before.
- Java enum constants: each constant declaration is a call from `Enum#<clinit>` to `Enum#<init>`, constructor (high when the enum is in the scan), on the constant's line.
- Top-level / file-level code (outside any function or type): the caller is the file's module ID. Languages with a module qualifier use it (Python module, JS/TS module, Lua module, OCaml/Haskell module, Rust module path `crate::a::b`, Groovy `pkg.Script#run`). Languages without one (Ruby, PHP, C, C++, ObjC, Zig file scope) use the file path below the scan root without extension (`lib/devise/rails/routes`). An empty caller or `<global>` is a wrong caller.
- Typed receivers (decision A, all statically typed languages and typed PHP/Groovy declarations): a receiver whose type is given by a declaration — local, parameter, field/property (including `$var->prop` / `obj.field` chains whose property has a declared type), catch parameter, for-loop variable, pattern binding — or by `= new T(...)` gives `T#m` (high if defined in the scan, else medium). A type variable resolves to its declared bound (C++: a concept that pins one type, `std::same_as<T>` / `derived_from<T>`; otherwise unconstrained, stays low). An enum constant `E.C` has type `E`. A type alias (`using X = T;`, `typedef T X;`, Zig `const X = a.b.T`) is expanded to its target, so the ID names the real type (`std.map#begin`, not `SafeStringMap#begin`); a declared type resolves through the file's using-directives and using-declarations, including those of headers it includes.
- Honest low (do not resolve by guessing): calls resolved only at runtime through a closure delegate (Groovy), query/DSL names read by a macro (Ecto `field`, `type`), and types reachable only through more than one wildcard import.
- Not calls: passing a method reference (`x::m`, `self.m` without call), enum-variant/data construction (Rust `Some(x)`, `E::V(..)`, Haskell `Con {..}`), casts, language constructs (`isset`, `empty`, `sizeof`), declarations/function heads, module attributes, typespecs, field access without a call.
- Generic/template type arguments are dropped from every ID (`HashSet#<init>`). Overloads share one ID. Companion-object members flatten onto the class.

## Confidence tiers
- **high**: the callee is a function/method/constructor defined in the scanned source (the tool matched it to a definition).
- **medium**: the callee is named statically (Type.m(), module.f(), an import, `self.m()` inherited from a base outside the scan, an external library type) but is not defined in the scan.
- **low**: a guess — receiver of unknown type (`recv.m`, `.m`), or a bare name not found in the scan.
- **unknown**: a dynamic call (function value, callback, closure, function pointer).

## Per-language notes
- **Python**: module-qualified IDs from the package structure (directories with `__init__.py`): `pkg.mod.f`, `pkg.mod.C#m`, `pkg.mod.C#<init>`, nested functions `pkg.mod.f.inner` / `pkg.mod.C#m.inner`; module-level code's caller is the module name, class-body code's caller is `pkg.mod.C`. Imports (relative, aliased, star, re-exported via `__init__.py`) resolve to the defining module. Builtins are `builtins.len` (medium).
- **JavaScript / TypeScript**: module = the file's path below the scan root without extension and trailing `/index` (`src/chat` for src/chat/index.ts; basenames collide across directories): `src/app.f`, `src/app.C#m`, `#<init>`/`#<clinit>`/`#field` as in Java. TS namespaces and named object literals (bound at the top level or exported) nest with dots (`mod.ns.f`, `mod.obj.f`); the object `module.exports`/`export default` is, is the module (`mod.f`); `module.exports = fn` is `mod.default`. Imports, `require`, re-exports (`export *`, `export * as`) and workspace packages (package.json `exports`) resolve to the defining module; packages outside the scan are named as written (`node:http.createServer`, `zod.z.object`, medium). Receivers typed by a declaration or `= new Foo()` (decision A) give `Foo#m` (medium). Globals: `JSON.stringify`, `globalThis.parseInt` (medium). `this.x` assigned a value is a callback. Import statements are not calls.
- **Java / Kotlin / C# / Groovy / Scala**: package/namespace-qualified: `com.x.C#m`; an external type is qualified through its explicit import. Kotlin top-level functions `com.x.f`. A Groovy script (a file with top-level code or functions) is a class named after the file: its functions are `pkg.Script#f`, its top-level code `pkg.Script#run`.
- **Go**: package-path-qualified: `example.com/m/pkg.Type#Method`, `pkg.Func`; closures `pkg.F$1`. An interface call emits the call as written, `Interface#Method` (high/medium), plus one low edge per concrete implementation that type-flow analysis (VTA) shows can reach it; out-of-scan implementations only with include_external. A call through a function value is ONE edge whose callee is the variable/field name, callback, unknown.
- **Rust**: no module prefix: `Type#method` (impl and trait methods), free functions bare; module paths keep `::` (`std::env::var`); an external type keeps its path only where the scan defines a type of the same name, so the two stay distinct (C1: `core::cell::UnsafeCell#get` beside a scanned `UnsafeCell`; approved 2026-11-10 with the type-path fix); `Type::assoc` → `Type#assoc`. Macro invocations → call_type macro; calls inside macro arguments are ordinary edges. Closures bound to a `let`, and `fn` items nested in a function body, are named nested functions (`outer.f`); `crate::` paths and the package's own crate name resolve like module paths.
- **C / Objective-C**: function-like macros → call_type macro (high if `#define`d in the scan). C functions bare; ObjC methods `Class#selector` with keyword colons (`doX:withY:`); `[obj m]` → `obj.m`.
- **C++**: namespace-qualified with dots: `ns.Class#method`, `ns.func`; `Class::static()` → `Class#static`; template arguments dropped.
- **Ruby**: `Outer.Inner#method` (constants dotted); `Foo.new` → `Foo#<init>`; constants resolve lexically. A class whose ancestry reaches outside the scan — an external superclass or include, a reopened external class (`class ActiveSupport::TestCase`), or a computed superclass expression (`< Devise.parent_controller.constantize`) — names bare calls not defined by any scanned ancestor `Scope#m`, medium.
- **PHP**: namespace-qualified with dots: `App.Svc#run`; `$this->m()` → `App.Svc#m`; `Cls::m()` → resolved class `#m`.
- **Swift**: no module prefix; `Type#method`, `Type#<init>`; extensions' members belong to the extended type; computed-property getters and static-let initializers have caller `Type#property`.
- **Lua**: module = the name the scan's `require` strings give the file (`core.common` for data/core/common.lua; ambiguous matches go to the require root that explains the most requires; lite-xl relative `require ".x"` resolves against the requirer). Functions on the module's returned table are `mod#fn`, on another file-local table `mod.T#fn`, on a global table `T#fn`; local functions `mod.f` / `outer.f`; module-level code's caller is the module. `require` bindings resolve; `X = Base:extend()` is a superclass. Builtins `_G#pairs`, standard library `string#sub` (medium). Other `obj:f()` → `obj.f`.
- **Zig**: file-qualified: `file.Struct#fn`, `file.fn`; `@import` bindings make `std.x.y` medium.
- **Haskell**: module = the `module` header (else the file name); top-level functions, class methods and record fields `Module.f`; where/let bindings `outer.f`; instance methods `Module.Class.Type.m`. Bare names resolve through local bindings, the module, import lists (with `T (..)` fields and hiding), unqualified imports of scanned modules (following `module M` re-exports and export lists), the Prelude (`Prelude.show`, medium) and the one unlisted external import; qualified imports `Map.size` medium. `f $ x` and `x & f` call f. Applying an argument is unknown.
- **Elixir**: `Module.fun`; `defimpl P, for: T` members → `P.T.fun`; aliases (lexical, in source order; `require M, as: R`; a nested `defmodule` aliases itself in its parent) resolve to the full module; remote calls `Mod.fun` medium unless defined in the scan; code outside any module has the file's module as caller.
- **OCaml**: top-level `file.fun` (file basename); nested modules/functors dotted (`file.Make.connect`); local function lets `outer.f`, local value lets fold into the enclosing binding; module-level code's caller is the module. Names resolve in definition order through local bindings, local opens, enclosing structures and their opens/includes, module aliases (`module F = Filegen.Make (P)`) and dune library wrappers (`Functoria.DSL`); then Stdlib (`Stdlib.invalid_arg`; when the scan contains the standard library's own sources, its definitions instead: see Decisions 2026-11-12), the innermost external local open, the one external open (medium); `List.length` medium; applying a parameter is unknown.

## Decisions (2026-10-29): each picks what the code does at runtime
- **Typed receivers (decision A) cover every declaration of the receiver's type**: locals, parameters, fields, and file-scope globals/statics (C, C++, ObjC, Zig, Rust `static`). A pointer, reference or smart pointer whose `->`/`.` reaches the pointee names the pointee: C++ `unique_ptr<T>`/`shared_ptr<T>`/`T*`, Rust `Box<T>`/`Rc<T>`/`Arc<T>`/`&T` → `T#m`, unless the wrapper itself defines `m` (`p.clone()` on an `Arc` is `Arc#clone`). A container is its own type: `Option<T>#unwrap`, `Vec#push`.
- **Rust constructors type their binding**: `let x = T { .. }` and `let x = T::new(..)` / `T::default()` / `T::with_capacity(..)` give `x` type T; an in-scan associated function gives its declared return type (`-> Self`/`-> T`). The same holds for the in-place chain `T::new(..).m()`. Ruled 2026-11-12, as the most accurate reading: a method only `Result`/`Option` define (`unwrap`, `expect`, `unwrap_or*`, `unwrap_err`, `expect_err`, `is_ok`, `is_err`, `is_some`, `is_none`, `map_err`, `ok_or*`) on such a receiver shows the constructor is fallible (`NonZeroU64::new(5).unwrap()`, `Runtime::new().unwrap()`). That call stays a low guess, in a chain or through a `let`, unless T itself defines the method. A scanned alias of `Result`/`Option` (`type DeltaResult<T> = Result<T, E>`) is a `Result`/`Option`.
- **Implicitly imported names are qualified**: Java/Scala/Groovy `java.lang.String`, Groovy's default imports (`java.util.List`, `groovy.lang.Closure`, …). With exactly one on-demand import (`import a.b.*`), a simple type name that is not in the file's package, not imported singly and not a java.lang type is `a.b.Name` (medium); with more than one such import it stays unqualified, low.
- **Go**: calls in package-level `var` initializers have caller `pkg.init` (they run during package initialization). Builtins (`len`, `append`, `make`, `panic`, …) are not calls: no edge.
- **Objective-C**: `[[T alloc] init…]` is `T#alloc` plus `T#init…` (the init runs on a T); a receiver typed `id<P>` names the protocol, `P#sel` (medium unless P is in the scan). Dot-syntax property access is not a call.
- **Objective-C++ (.mm)**: C++ constructs follow the C++ rules (`Cls::m` definitions, member calls, constructors); message sends follow the ObjC rules.
- **Elixir**: guards are calls of their function. `:erlang_mod.f` and an imported Erlang module are `erlang_mod.f`. A `use`d module's injected imports and aliases resolve through its source (the scan, dependency sources, the standard library); with one import known to export the name, that import is the target. `def unquote(:name)` with a literal name is `Mod.name`; `defimpl P, for: [A, B]` members are `P.A.f` and `P.B.f` (one edge per type).
- **Python**: a call to an external capitalized function that is not known to be a class is a direct call to it (`mod.Name`), not `Name#<init>`. Known to be a class (clarified 2026-11-12): a builtin (`builtins.ValueError`) or a standard-library class (`pathlib.Path`, `threading.Thread`, `argparse.ArgumentParser`, `collections.Counter`, `subprocess.Popen`, …), not a capitalized standard-library factory function (`multiprocessing.Pool`, `tempfile.NamedTemporaryFile`). A third-party name (`torch.utils.data.DataLoader`) is not known.
- **Lua / Zig**: a local or const alias of a function (`local insert = table.insert`, `const assert = std.debug.assert`) resolves to its target.

## Decisions (2026-11-09): scope and two tiers, fixed so every reviewer rules alike
- **Scope is everything the tool scans**, except paths with a segment named exactly `test`, `tests`, `spec`, `examples` or `docs`. Vendored and third-party code (`external/`, `vendor/`, `third_party/`, `Pods/`), generated files (generator headers, protobuf/FreeGen output), fixtures (`scalafix/input`), Xcode `*Tests/` targets, `example/` (singular) and `benchmarks/` are all IN scope and judged like any other code. Do not exclude anything else, and do not offer an alternative scope in the report.
- **Parameterless members are typed receivers (decision A)**: a receiver that is a call of a parameterless method, a `def` without a parameter list, a property getter, or an abstract member, with a declared type (Scala `def metadata: Map[..]`, `analysis.metadata.insert(..)`), names that type: `Map#insert` — left as a `metadata.insert` low guess it is wrong.
- **Typing reaches only declarations in the scan**: decision A and the parameterless-member rule use declared types written in the scanned source (including vendored code). A receiver whose type is only knowable from a library's signatures outside the scan (`project.tasks.named`, `entrySet().removeIf` on a JDK/Gradle type) stays a low guess, and that is correct.
- **gtest bodies are the methods gtest generates**: `TEST_F(Suite, Name) { … }` / `TEST_P` / `TYPED_TEST` define class `Suite_Name_Test` derived from the fixture `Suite` (`TEST` from `testing::Test`); the body's caller is `Suite_Name_Test#TestBody`, and bare calls and fields in it resolve through the fixture. gtest/gmock assertions (`ASSERT_*`, `EXPECT_*`, `GTEST_SKIP`, `SCOPED_TRACE`, …) are function-like macros: macro, medium.
- **Body-less member declarations of scanned types are defined in the scan (high)**: a call that resolves to a method declared without a body by a trait, interface, protocol, abstract class or pure-virtual C++ declaration (`fn now() -> u64;`, `virtual void OnError() = 0;`, `def m: Int`, an interface method) is high when that declaring type is in the scan, exactly as Go interface calls are. A free-function prototype whose definition is not in the scan (a C header declaring a library function) is still medium.

## Contracts (2026-11-10): what every edge and node satisfies
These hold in every language. A builder that violates one has a defect, whatever any repo's census says.
- **C1 Symbol identity.** Every definition has exactly one ID. Every reference to it uses that ID: a call in the defining file, through an import, a re-export, an alias or a `require` binding. A definition that edges reach is listed in `nodes`, including body-less member declarations of scanned types (interface/trait/protocol methods) and module-level bindings that hold a function. A high edge's callee is always in `nodes`.
- **C2 Resolution consistency.** The same written reference in the same scope resolves the same way wherever it occurs. Resolution does not depend on file order, the scan root, or which other files are present, except through the definitions those files supply. An ID is never invented: a medium or high callee that names a member of a scanned module or type (`mod.T#f`, `mod.f`) is defined there, or is inherited from a base outside the scan.
- **C3 Operation classification.** Each written construct is exactly one of:
  - an invocation: `direct`, `method` or `constructor`;
  - a dynamic invocation, meaning a call through a value: `callback`, unknown;
  - a macro invocation: `macro`;
  - implicit execution: `implicit`;
  - one of these, which emit no edge: a module dependency (an import declaration; the binding carries it), data construction or a pattern, a declaration, or a reference without a call.
- **C4 Unresolved references are preserved.** A call the tool cannot resolve is still emitted as a low guess (`recv.m`, `.m`, a bare name). It is never dropped and never promoted to a resolved ID. Silence in the graph means no call, or a `coverage` note.
- **C5 Confidence is not identity.** The callee ID comes from resolution alone. Confidence and call_type report the evidence for it. A tier is never raised, and an ID never substituted, to make an edge look resolved.
- **C6 Determinism.** The same source and the same tool build give the same edge multiset and the same node set on every run, whatever the output order.
- **C7 Complete edges.** Caller and callee are never empty. The line is the line of the callee's name, per the ID-format rules.

## Change control (2026-11-10)
- The Decisions sections are approved rulings. A ruling reopens only for:
  - (a) a reproducible counterexample, where the rule contradicts what the code does at runtime;
  - (b) a violation of a contract C1–C7;
  - (c) a construct the spec does not cover;
  - (d) new correctness evidence, such as the language reference or compiler behaviour.
- A reviewer's disagreement does not reopen a ruling. Neither does a repo's census, nor the cost of a builder change.
- Every finding gets one disposition before any code changes:
  - **implementation defect**: fix it test-first, with a golden fixture;
  - **spec ambiguity**: a new dated ruling under this rule, plus a fixture, then the implementation;
  - **reviewer error**: re-judge it against this spec, with no code change;
  - **methodology limitation**: change REVIEW_PROMPT.md or the method, with no code change;
  - **accepted limitation**: record it in CAPABILITIES.md, with a coverage note where the tool can detect it.
- Every change to builder output is diffed against the approved baseline. Every changed edge group gets one of these dispositions before the change is accepted (gates/README.md).

## Decisions (2026-11-10): four rulings, by runtime semantics and the contracts
- **CommonJS / Lua `require`.** A `require(...)` call (JS) or `require "m"` (Lua) is an invocation of the loader: callee `require` (JS) or `_G#require` (Lua), medium, direct, on its line. The edge is not the module dependency. The binding carries the dependency: names bound from it resolve to the defining module, using its IDs when it is scanned and the specifier as written when it is not (`node:http.createServer`, medium). A `require` whose argument is not a literal leaves its bindings unresolved (low guesses), per C4. An ESM `import` declaration is not a call. A separate module-dependency output is not provided (CAPABILITIES.md).
- **Lua functions stored on a table.** `function T.f()`, `function T:f()` and `T.f = function` name the function when `T` has a static identity. Both forms get the same ID:
  - the module's returned table: `mod#f`;
  - another top-level local: `mod.T#f`;
  - a global: `T#f`;
  - a required module: that module's ID;
  - a local inside a function that is bound to a table constructor (`local T = {}` or `local T = { … }`) and never reassigned in its scope: `mod.T#f`. Every such table of that name in a file shares the ID, as overloads do.

  Calls `T.f()` and `T:f()` on such a table resolve to that ID (high when defined). A table without a static identity gives no name. That means a function-local table that is a parameter, a reassigned local, or a local bound to a call result or other expression, and any computed index. A top-level local always has a static identity (`mod.T#f`), including `local X = Base:extend()`, which is also a superclass. A function stored into it, in either form, folds into the enclosing function, and calls on it stay `T.f`, low.
- **Elixir records.** `defrecord` and `defrecordp` (bare after `import Record`, or `Record.defrecord` after `require Record`) declare record macros. Like `def` and `defstruct`, they are declarations: no edge. Calls written in their arguments are ordinary edges, for example `Record.extract(:x, from_lib: …)`, medium.

  A use of a record macro declared in the file, or imported from a scanned module, emits no edge. Such a use builds, matches, updates or reads a tuple at compile time. That covers expression and pattern position alike: `listener(node: n)`, `handler(:id)`, `rec(r, field: v)`. This is data construction. Calls in the use's arguments are ordinary edges. A record generates no runtime functions, unlike macros that do (`defdelegate`, `defexception`), whose generated functions are call targets.
- **JS/TS module-level bindings.** A top-level binding has one ID, `mod.name`, from its own file and from every importer, per C1. That covers `const`/`let`/`var`/`export const`, a function declaration and a class. A call through it uses that ID everywhere, never the bare name in its own file. call_type and confidence follow the evidence that the value is a function, per C5:
  - **Function literal.** The initializer is a function literal: a named function (existing rule).
  - **Alias.** The initializer, after removing parentheses, `as`, `satisfies` and `!`, is an identifier or member path that names a function (`isArray = Array.isArray`, `render = baseRender as RootRenderFunction`). The call resolves to that function's ID, as Lua/Zig aliases do.
  - **Function type.** The binding's type annotation or an `as` cast of its initializer is a function type (`camelize: (str: string) => string`, `as typeof _createVNode`). Callee `mod.name`, direct, medium.
  - **Function factory.** The initializer is a call of a scanned function that returns a function literal: its arrow body is one, a top-level `return` returns one, or its declared return type is a function type. Examples: `cacheStringFunction(fn)`, `createHook(…)`, an IIFE `(() => (x) => …)()`. Callee `mod.name`, direct, medium.
  - **No evidence**, as in plain JS `x = f()` with `f` not scanned: callee `mod.name`, callback, unknown. This is a call through a value, under the binding's canonical ID.

  Medium, not high: the tool matched a binding, not a function body. An alias takes its target's tier: high when the target function is defined in the scan.
- **`direct` vs `method`** (raised by every golden-corpus author; previously undefined). Among invocations, `call_type` follows the callee's identity:
  - `method`: the callee is a member of a type, `T#m` other than `T#<init>`. That covers instance, static, class and companion methods, a bare call of an enclosing type's member, and `self.m()`/`this.m()`. A receiver guess (`recv.m`, `.m`) is also `method`.
  - `direct`: every other named callee. That covers free functions, module, package and namespace functions (`mod.f`, `pkg.F`, `Module.fun`, `ns.f`, `JSON.stringify`, `std.fmt.parseInt`, `Data.Map.size`), named nested functions (including those of a method, `T#m.f`), builtins, and a bare unresolved name.
  - Lua is the one exception, because its ID notation puts table functions under `#`. A call written `T:f()`/`obj:f()` passes `self` and is `method`. A call written `T.f()`/`obj.f()` passes nothing and is `direct`, whatever its ID.
  - `constructor`, `callback`, `macro` and `implicit` keep their definitions. An `implicit` edge has the tier of its target, high for a field of a scanned type.

## Decisions (2026-11-10, golden corpus): rulings on questions the independent fixture authors raised
Each picks what the code does at runtime. The open questions are listed in GOLDEN_AUTHOR_QUESTIONS.md; this section decides the ones the corpus needs now.
- **Typed call results.** A receiver that is a call result, an index or a literal is typed when its static type can be determined from declarations: a declared return type in the scan, or the language's type checker (Go). Then `b.Add(1).Add(2)` is `Builder#Add` (high when scanned). `.m` (low) is for receivers whose type is not determined. This extends the parameterless-member rule of 2026-11-09 to calls with arguments.
- **Go types through its type checker.** The Go builder type-checks the program, so a receiver typed only by a library signature names the library type: `strings.Reader#Len`, `time.Time#Unix`, medium. The 2026-11-09 rule "typing reaches only declarations in the scan" sets the minimum for the other languages. It does not make a correctly resolved library type wrong.
- **Known external exports.** Where the tool has an index of an external module's exports (the Elixir standard library and dependency sources, the Haskell base libraries), a bare name resolves to the one imported module known to export it, at medium. Haskell is now treated like Elixir (`Data.Maybe.fromMaybe` with `import Data.Maybe` among several unlisted imports). Elixir also follows the Haskell/OCaml rule: with exactly one unlisted external import, a bare name not otherwise defined is that module's, medium.
- **Elixir file-level code.** Its caller is the file's path below the scan root without extension (`lib/boot`), as for the languages without a module qualifier. An Elixir file may hold any number of modules, so no module name is "the file's".
- **Generated functions have no written body.** A call of a function that a scanned macro generates (`defexception`'s `exception`/`message`, a `defdelegate`'s function) is named by its ID at medium, as a JS/TS binding is.
- **Rust macro IDs keep the `!`**, as written: `println!`, `vec!`, `square!` (high when `macro_rules!` defines it in the scan; the macro is then a node).
- **Ruby `Kernel`.** A bare call of a `Kernel` method (`puts`, `require`, `raise`, `format`, …) is `Kernel#puts`, medium, method. That is where it is defined at runtime, as Python's are `builtins.len`.
- **C# external types are named as written.** An external type is not expanded through `using` directives: `Exception#<init>`, `List#Add`, medium. A C# file usually has several usings. Types declared in the scan resolve to their namespace as before.
- **(Already decided; author's reading corrected.)** A call of a member inherited from a superclass outside the scan is `Type#m`, medium, named by the calling type (ID format: "If `m` is defined only on a superclass that is in the scan, the callee is `Superclass#m`"; otherwise it stays on the type). Example: Groovy/Scala `Worker extends Thread`, `start()` is `zoo.Worker#start`.

## Decisions (2026-11-10, amendment): counterexamples from the baseline diff
Raised under change control by the gate diff of the fixes build against HEAD. Each case is a ruling's own example or a construct the ruling did not cover. Each has a golden fixture.
- **JS/TS function types through a type alias.** Function-type evidence covers a type alias whose definition is a function type, generic or not. The alias can be declared in the file, or imported and re-exported. Example: `render = baseRender as RootRenderFunction<E>` with `type RootRenderFunction<E> = (vnode, container: E) => void` is `mod.render`, direct, medium, as for `as (x) => void`. Here `baseRender` is destructured from a call, so the Alias rule does not resolve it, and the cast's type decides. That is the ruling's own vue example. An alias of a non-function type (`type Box = { v: number }`) is no evidence.
- **JS/TS conditional initializers and factory returns.** A conditional `c ? a : b` is evidence when every branch is. A branch counts if it is a function literal, an alias of a function, a factory call, or such a conditional. Examples: `calcRound = cond ? Math.fround : (function () { … })()`, `nextTick = p ? function (fn) {…} : function (fn) {…}`. A factory returns a function when a top-level `return` gives one of those, or a function declared in its body (`makeBrotliDecode = () => { function decode() {…} return decode; }`). A declared return type that is a function type, directly or through an alias, also counts. Each is `mod.name`, direct, medium. A JSDoc `@type` comment is not evidence. A branch with no evidence, such as a value binding, makes the whole conditional no evidence.
- **Lua tables of external modules.** A local bound to `require` of a module the scan does not define, or to a member of one, gives no name to a function stored on it. Examples: `resolver.new = function` with `local resolver = require "resty.dns.resolver"`, or `utils.readlines = function` on `pl.utils`. Such a function is a test's mock or a patch. It is not the library's definition, and naming it with the library's ID would give two definitions one ID (C1). It folds into the enclosing function. Calls of the library stay the library's ID at medium, including the mock's call of the saved original.
- **JS/TS `.bind` of a function.** `Function.prototype.bind` always returns a function. So `X.bind(…)` is evidence when `X` is: a function literal, a scanned function declaration, an alias of a function, or a binding that already has evidence. A call through the binding is `mod.name`, direct, medium (superseded 2026-11-12 where the target can be named: see Decisions (2026-11-12), `.call`/`.apply`/`.bind`). Example: `isValidExplicitDest = _isValidExplicitDest.bind(null, isRefProxy, isNameProxy)` in pdf.js's api_utils.js, with `_isValidExplicitDest` imported from shared/util.js. `.bind` on a value with no evidence (`obj.bind(…)` where `obj` is a parameter or an unknown value) is no evidence: it could be any object's `bind` method. (Raised 2026-11-10 by the final-build gate diff; decided by the maintainer.)

## Decisions (2026-11-12): rulings on readings the 2026-11-11 and 2026-11-12 re-reviews found SPEC left open
Decided by the maintainer, each for the option closest to what the code does at runtime. Each has a contract test and a golden fixture.
- **JS/TS local object literals fold.** An object literal bound inside a function (`test('x', () => { const Comp = { setup() { … } } })`) is not named: its methods fold into the nearest enclosing named function, or the module at top level, per the ID-format rule. Only object literals bound at the top level or exported are named (`mod.obj.f`). Reason: dozens of tests each declare their own `const Comp`, and naming them gives many definitions one ID (C1).
- **A scanned standard library is the scan's own code.** When the scan contains a language's standard-library sources (the OCaml compiler's `stdlib/stdlib.ml`), a call of one of its functions resolves to that definition's ID at high (`stdlib.print_string`), as `List.map` resolves to `list.map`. The external form (`Stdlib.print_string`, medium) is for scans that do not contain the definition. Reason: C1, one definition, one ID; the external form hides every caller from the definition.
- **Generated functions cover C/C++/ObjC macros, narrowly.** The golden-corpus ruling "Generated functions have no written body" applies to a scanned function-like macro invoked with literal arguments whose expansion defines a function, including names built with `##` (`#define DEFINE_HIDE(name) void hide_##name(…) {…}` with `DEFINE_HIDE(func)` defines `hide_func`). A call of such a function is named by its ID at medium; the declarations the expansion makes (a function's declared return type) type receivers as written declarations do. A nested expansion is expanded too (widened 2026-11-12): when the substituted body invokes another scanned function-like macro whose arguments are still literal, that macro's generated functions are generated as well, through any depth of such forwarding (`#define WASM_DEFINE_TYPE(name, Name) WASM_DEFINE_OWN(name, Name)` with `WASM_DEFINE_TYPE(valtype, ValType)` defines `hide_valtype`). A literal argument is an identifier, a number, an empty argument, or a lone pointer/reference declarator (`*`, `&`, as in `WASM_DEFINE_VEC_BASE(name, Name, vec, vec, )` or `…, *)`). Expansions that are conditional, or built from expression arguments (`a + b`) at any level, are not expanded: calls stay low guesses.
- **JS/TS `.call`, `.apply` and `.bind` (question 80).** Per ECMA-262 §15.3.4.3–15.3.4.5: `.call`/`.apply` check that the receiver is callable and invoke its [[Call]] on that line; `.bind` creates a bound function that has no [[Code]] of its own and whose [[Call]] invokes the target's. Only a receiver with function evidence (the JS/TS binding ruling: a function literal, a scanned declaration, an alias of one, or a binding with evidence) is treated as a `Function.prototype` method; `angular.bind(…)`, `goog.bind(…)`, `client.call(…)` stay receiver guesses.
  - `f.call(t, …)` / `f.apply(t, …)` emit **two edges** on the line: `Function#call` / `Function#apply` (method, medium) and the target `f` (direct, or method when `f` is `T#m`; at `f`'s tier). This is the one construct with two edges for one written invocation: two functions run.
  - `X.prototype.m.call(…)` names the target by its type: `Object.prototype.hasOwnProperty.call(o, k)` gives `Function#call` and `Object#hasOwnProperty` (method; high when `X` is scanned and defines `m`, else medium).
  - A function-literal receiver (`(function () { … }).call(this)`) is an immediately invoked function: only `Function#call`/`#apply`; its body folds into the enclosing function.
  - `f.bind(…)` emits `Function#bind` (method, medium). A call through a binding `v = f.bind(…)` resolves to `f` at its tier, as the Alias rule does; when `f` cannot be named (a function literal), it is `mod.v`, direct, medium.
  - An imported function's own members (`g.extra = function` in its file) have one ID, `mod.g#extra`, from every file (C1).
  - Not supported: the `this` rebinding itself. `Body.call(Response.prototype)` gives the edge `→ Body`; the methods `Body` installs through `this.x = function` stay `Body`'s (KNOWN_GAPS).
- **A local bound to a call result takes the callee's declared return type** (approved 2026-11-12; golden question 57). With no written type, `let s = f(); s.m()` (Rust `let`, Swift `let`/`var`, Kotlin `val`, Scala `val`, Java/C# `var`, and the like) is typed as the in-place `f().m()` is under "Typed call results": `T#m`, high when T is in the scan, medium when it is not. `?`, `.await` and smart-pointer unwrapping apply as they do in place. A generic, tuple, overload-ambiguous or undeclared return type leaves the call a low guess. A local's static type is fixed at its declaration, so assigning it again (`let mut`, `var`) does not untype it.
- **Optional chaining types through `?.`** (approved 2026-11-12). `x?.m()`, `f()?.m()` and `T(raw:)?.m()` name the method a typed receiver names (`T#m`), as `x.m()` would: `?.` decides only whether the call runs, not which method runs. A `T?` declaration types its receiver as `T`.
- **Readings applied at the 2026-11-12 final5 gate** (applications of the smart-pointer rule above, C2 and the let-bound bullet; no new ruling). `.await` names a declared output only for a call to a scanned `async fn` (Rust); a TS `await` of a call declared `Promise<T>` is a `T`; a value awaited through `IntoFuture` (a builder) has no declared output, so calls on it stay guesses. Smart pointers include the borrow and lock guards (`Ref`, `RefMut`, `MutexGuard`, `RwLockReadGuard`, `RwLockWriteGuard`): `self.emit().f()` with `emit() -> RefMut<'_, Builder>` is `Builder#f`. A scanned, non-generic alias of a smart pointer (`type SchemaRef = Arc<StructType>`) is expanded before it is dereferenced, unless the file names an external crate's item of that name (`use arrow_schema::SchemaRef`, or the path written in full). A path is an external crate's when it does not start at `crate`, `self` or `super` and passes through a segment that is neither a scanned module nor a workspace crate: `datafusion::physical_plan::SendableRecordBatchStream` is datafusion's even in a scan with its own `mod datafusion`. A trait object's extra bounds inside a generic argument belong to that argument (`Pin<Box<dyn RecordBatchStream + Send>>` is a `Pin`). A type that derefs to its own type parameter (`impl<T> Deref for Guard<T> { type Target = T; }`) has an unknown pointee for a method it does not define. A raw pointer (`*mut T`), a TS type alias and a mapped utility type (`Readonly<T>`, `type DeepReadonly<T> = …`) name no type of their own: calls on them stay guesses. "Overload-ambiguous" includes declarations of one ID whose return types differ or of which one declares none (Kotlin `fun f(): A` beside `fun f(n: Int): B`, C++ overloads, a `void` overload). Return types are compared after resolving the scan's type aliases, so the C++ const-overload pair `reference at()` / `const_reference at() const` agrees. For C2, a Lua module's members include the fields of a table constructor it returns or binds (`return { setenv = misc.setenv }`, `setmetatable({ … }, mt)`).

## Decisions (2026-11-16): three rulings for the option most accurate to the code (maintainer, 2026-11-16)
Each reopened under Change control (d), language semantics; each has a contract test.
- **Groovy `def` locals bound to a call** (the 2026-11-12 let-bound ruling, applied to Groovy). `def x = f(…); x.m()` is typed by `f`'s declared return type, as in place, when that type is concrete: not `def`, `Object`, `void` or a type parameter (`def <T> T pick(T a)`), and not ambiguous across overloads. A scanned type names `T#m` (high when T defines or inherits m); an external one `T#m` medium. Because `def` is dynamically typed, a `def` local assigned again after its declaration (`x = other()`) is not typed: the 2026-11-12 "assigning it again does not untype it" holds for statically typed locals only. A method `Object` lacks (golden groovy/06's `x.fire` after `Object make()`) runs by Groovy's dynamic dispatch on the runtime object and stays a low guess. Test: groovy `DefLocalBoundToTypedCall`.
- **Rust: a crate's impl for a smart pointer is found before the deref.** With `impl<T: Tr + ?Sized> Tr for Arc<T>` in the scan, `x.m()` on an `Arc<P>` receiver whose pointee P satisfies T's bounds (`dyn Tr`, or a type the scan implements them for) runs the impl's method: `Arc#m`, as Rust's method lookup finds the receiver's own impls before auto-deref. Without such an impl, or when P does not satisfy the bounds, the smart-pointer rule applies (`P#m`). `?Sized` is not a bound, so `T::m(self)` inside the forwarder names `Tr#m`. Tests: rust `CrateImplForArcWinsWhenBoundHolds`, `SmartPointerAliasDereferences`.
- **Compile-time constants run no initializer (Java, Kotlin; as C# `const`).** A Java constant variable (JLS 4.12.4: a `static final` field, or an interface field, of primitive or `String` type whose initializer is a constant expression, 15.29: literals other than `null`, operators over constants, casts to a primitive or `String`, simple names of such fields) and a Kotlin `const val` are inlined at their uses and initialized from the class file's `ConstantValue`: no `<clinit>` code runs, so there is no implicit edge. A boxed type (`Integer`), an object, a call, `null`, or a non-final static does run and keeps its implicit edge. Interface fields that are not constants are initialized in the interface's `<clinit>` (`Consts#<clinit> → Consts#NAME`) and are fields of the interface (C1). Tests: java `CompileTimeConstantsHaveNoImplicitEdge`, kotlin `ConstValHasNoImplicitEdge`.

## Decisions (2026-11-17): in-place constructor results (maintainer, 2026-11-17, the option most accurate to the code)
Reopened under Change control (c), a construct the spec did not cover; each language has a contract test.
- **An in-place constructor result is typed as the bound form is.** `new T(...).m()` (Java, Groovy, C#), `T(...).m()` on a class T (Kotlin, Scala `new T(...)` and a case-class `T(...)`) is `T#m`, high when T is in the scan and defines or inherits m, medium when T is outside the scan, exactly as `x = new T(...); x.m()` under decision A and Rust's in-place `T::new(..).m()`. A parenthesized receiver `(new T()).m()` is the same. An anonymous subclass (`new T() {…}.m()`) may define m itself and stays `.m`, low. Kotlin types an external `T(...)` in place as `val x = T(...)` is (medium), except a known external factory function (`MutableStateFlow(0)`), which types neither form; Kotlin's `!!` unwraps as Rust's `?` does (`val e = cache.edit(k)!!; e.commit()` and `cache.edit(k)!!.commit()` are `Editor#commit`). A secondary constructor's declared parameters type their receivers as a function's do. Under "Typed call results", an index of a declared array (`Node[] nodes; nodes[i].m()`, a varargs parameter `Node... rest`, an array-returning method `all()[2].m()`) is its element type; a call on the array itself (`nodes.clone()`) names no type.

## Method
1. Load the tool JSON with python3/jq (it can be large — never print it whole). Only judge edges whose source_file is in the repo's main language and NOT under a path segment named test/, tests/, spec/, examples/ or docs/ (see Decisions 2026-11-09: vendored, third-party, generated and fixture code IS in scope).
2. PRECISION: sample 50 edges stratified by confidence (roughly proportional to tier counts, at least 5 per tier that exists), spread over at least 15 files, random with a stated seed. For each, open source_file at line_number and judge: real call? caller correct? callee correct per spec? confidence correct per tiers? line correct?
2b. CENSUS: a 50-edge sample cannot separate 95% from 99%. For every wrong pattern you find (in the sample, the recall check, or by looking), count by script how many in-scope edges share it. Report `census precision = 1 − wrong/in-scope` and list the counts. Spec gaps are counted separately, never as wrong.
3. RECALL: pick 3 non-trivial functions (8+ lines, different files). Read each body, list every call it makes, compare with the tool's edges whose caller_id is that function. Report missed calls and edges that are not calls.
4. Report only verified facts; quote the exact source line for every mismatch. Do not speculate about the tool's implementation.
5. CAPABILITIES.md (next to this file) classifies constructs per language. Count calls in a construct it lists as **unsupported** (no edges by design) as recall gaps, never as wrong edges. Count output matching an **open defect** as wrong.

## Report format
Write `<name>_report.md` next to the JSON and return the same content:
- Summary line: `precision X/50; census ≈P% (W wrong of E in-scope); recall: N missed of M real calls; K non-calls`.
- Mismatch table: file:line | source line | tool said (caller → callee, confidence, call_type) | correct per spec | category (wrong caller / wrong callee / wrong confidence / not a call / missed call / wrong line / spec gap / other).
- Mismatch table rows also get a short root-cause phrase.
- Systematic patterns (a mistake you saw repeat), each with its scripted count, ordered by count.
