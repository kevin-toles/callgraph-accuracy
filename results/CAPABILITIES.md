## c

**Unsupported (by design):** directories named vendor/, node_modules/, build output and fetched dependencies are skipped (coverage: skipped).

**Undecided by SPEC** (no expectation; see GOLDEN_AUTHOR_QUESTIONS.md):
- `c/12-gap-xmacro`: For an X-macro list file included inside a function body (colors.def included in paint_all, with X defined by the including file): (1) is the caller of the X(red)/X(green) invocations paint_all (the inclusion site) or colors.def's file-level ID 'colors' (TOP rule applied to the fragment file)? (2) are the calls the expansion produces (paint_all → paint_red, paint_all → paint_green, direct, high) required edges, and if so with which file and line — colors.def:1/2 or paint.c:6? (3) are the X(...) invocations themselves macro edges to 'X' (high, #defined in paint.c)? SPEC covers calls in macro arguments, not calls created by expansion or token pasting.
- `c/13-libc-calls`: Is a call to a C standard-library function whose only declaration is in a system header outside the scan (strlen via #include <string.h>, malloc via <stdlib.h>) medium ('named statically ... an import ... an external library type') or low ('a bare name not found in the scan')? Does its ID stay bare ('strlen') or get a qualifier? And when the system header implements it as a function-like macro (memcpy under _FORTIFY_SOURCE), is it call_type macro (medium) or direct?

**Known gaps closed** (their golden case passes):
- c: definitions in .inl files and static inline header functions are under-resolved

**Unsupported (by design):** directories named vendor/, node_modules/, build output and fetched dependencies are skipped (coverage: skipped).

- `csharp/07-typed-receivers`: receivers bound by is-patterns (x is Item matched) stay low
- `csharp/08-interface-abstract-bounds`: type parameters with a where-bound are named T#m, not the bound
- `csharp/09-local-functions-lambdas`: a lambda bound to a local is not a named nested function

**Undecided by SPEC** (no expectation; see GOLDEN_AUTHOR_QUESTIONS.md):
- `csharp/17-extension-methods`: Which ID does a C# extension-method call get? In Note#Loud, `this.Shout()` (and `n.Shout()` on any receiver typed Note) runs the static method App.TextExt.Shout. Decision A says a typed receiver gives `T#m` = App.Note#Shout, but C2 forbids that ID because Note defines no Shout. Is the callee App.TextExt#Shout (method, high), App.Note#Shout, or a low guess? The same question decides LINQ (`list.Where(...)` on a List<T>: System.Linq.Enumerable#Where vs System.Collections.Generic.List#Where, medium).
- `csharp/18-property-read`: Is reading a C# property whose getter is user code (`Balance` in Report, or `obj.Balance`) a call edge from App.Account#Report to the accessor App.Account#Balance (call_type method, high), or a field access without a call (no edge)? SPEC defines callers inside accessors (Type#Prop / Type#Prop=) but not whether a property read or assignment invokes them; for Objective-C it rules dot-syntax property access is not a call, for C# it is silent. An assignment `obj.Prop = v` raises the same question for Type#Prop=.

**Known gaps closed** (their golden case passes):
- edges on attribute lines

## go

**Unsupported (by design):** directories named vendor/, node_modules/, build output and fetched dependencies are skipped (coverage: skipped); _test.go files are not analyzed; packages that fail to type-check are not graphed (coverage: go_package_load_error).

**Open defects** (golden case fails; wrong output when it occurs):
- `go/07-builtins-casts-not-calls`: a call through a method value (bark := d.Bark; bark()) is named Dog#Bark medium instead of the callback rule
- `go/14-gap-generic-types`: calls into scanned generic types are medium, not high
- `go/15-gap-package-var-init`: calls in package-level var initializers get no edges (SPEC Decisions 2026-10-29 requires caller pkg.init)

**Accepted limitations:**
- `go/16-gap-typecheck-failure`: a Go package that fails to type-check is not graphed; the coverage note go_package_load_error says so

**Undecided by SPEC** (no expectation; see GOLDEN_AUTHOR_QUESTIONS.md):
- `go/10-named-local-closure`: For Go `f := func(n int) int { … }` inside Compute, is the literal a named nested function (general rule: ID example.com/m.Compute.f, the call f(v) is direct/high to example.com/m.Compute.f, and double(n) has caller example.com/m.Compute.f) or a Go closure (Go note: ID example.com/m.Compute$1 as caller of double(n), and f(v) is a call through a function value: ONE edge, callee `f`, callback, unknown)? The general rule's list says local `func`, the Go note says closures `pkg.F$1` and function-value calls are callback/unknown; the two rules give different callers, callees, call_types and tiers for this construct.
- `go/17-gap-range-over-func`: Does `for x := range seq` (range-over-func, Go 1.23) emit an edge for the iterator invocation the language performs without a written call, seq(yield) — and if so which: callback/unknown to `seq` (a call through a function value), `implicit`, or for `range Count(3)` a low/VTA edge to the returned closure example.com/m.Count$1 — or no edge at all? Separately, is the caller of calls written in the loop body (process(x), fmt.Println(y)) the enclosing function example.com/m.Sum (the body is not a function literal in the source) or the compiler-synthesized yield closure? The body calls themselves are clearly required edges (process high, fmt.Println medium, Count high), but the case cannot be stated completely until the iterator-invocation question is ruled.
- `go/18-short-var-decl-typing`: Does a Go short variable declaration type its binding for decision A? `a := &Dog{}` (composite literal) and `b := NewDog()` (in-scan function with declared return type *Dog) have no written type on the local. Decision A lists declarations and `= new T(...)`; the Rust ruling had to add `let x = T { .. }` and in-scan constructor/return types explicitly, implying the general rule does not cover them. Is a.Speak() / b.Speak() example.com/m.Dog#Speak (method, high) or `a.Speak` / `b.Speak` (method, low)? The same question applies to C# `var x = Make();` (C# `var x = new T()` is covered by `= new T(...)`).
