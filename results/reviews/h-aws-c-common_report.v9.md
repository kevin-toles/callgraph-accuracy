## Systematic patterns (scripted, `h-aws-c-common_r9_census.py`)
Ordered by count. The union of wrong edges is 78 of 9,772, so census precision is 99.20%.

1. **44: function-pointer globals called as low direct.** The edges go to `_cbor_malloc` (29), `_cbor_free` (13), `_cbor_realloc` (1) and `tl_thread_handler` (1). Each is a file-scope variable of function-pointer type, so per SPEC the edge should be callback, unknown. The tool does this correctly for comparable globals such as `s_SymInitialize`, `s_p_time_func` and `g_numa_node_of_cpu_ptr`, which are callbacks, so this is also a C2 inconsistency.
   - Validation: allocators.c:10 `CBOR_EXPORT _cbor_malloc_t _cbor_malloc = malloc;`, common.h:117 `extern _cbor_malloc_t _cbor_malloc;`, error.c:19.
2. **20: edges emitted from `#define` lines in ittnotify.h.** 17 point into the replacement list (`ITTNOTIFY_VOID`, `ITTNOTIFY_DATA`, `ITTNOTIFY_VOID_D1`, `ITTNOTIFY_VOID_D5`). 3 are self-edges to the macro being defined.
   - No other `#define` in the scan produces an edge. In ittnotify.h itself, line 351 `#define __itt_pause_ptr ITTNOTIFY_NAME(pause)` and most sibling defines have none.
   - Validation: lines 350, 2889, 3095.
3. **9: calls of macro-generated functions left low.** The callees are `s_unsigned_int_val_callback` ×3, `s_negative_int_val_callback` ×3, `s_float_val_callback`, `s_cbor_decoder_pop_next_array_start` and `s_cbor_decoder_pop_next_map_start`, all in source/cbor.c.
   - They are generated by `LIBCBOR_VALUE_CALLBACK` and `S_GET_NEXT_ITEM` invoked with literal arguments. Decisions 2026-11-12 makes them medium.
4. **3: `isnan` in libcbor/encoding.c resolved high.** The only matching definition is a `#define` inside another `.c` file (cJSON.c:85).
5. **2: casts `(CFIndex)(…)` and `(KAFFINITY)(…)` emitted as calls.**

## Spec gaps (counted separately, never as wrong)
1. **c/13 (CAPABILITIES "Undecided"), 748 low direct edges.** These are calls of functions or macros whose only declaration is in a system or SDK header outside the scan: libc (`fprintf` 78, `malloc` 56, `printf` 38, `strlen` 30), POSIX (`pthread_*`, `dlsym`), Win32 (`GetProcAddress`, `GetLastError`), compiler-header intrinsics (`_mm256_*`, `_BitScanForward`), and header macros emitted as direct (`CPU_SET`, `CPU_ZERO`, `BCRYPT_SUCCESS`, `isfinite`, `htonl`).
   - Quoted constructs: `printf("Dumping hash table contents:\n");` and `DWORD current_thread_id = GetCurrentThreadId();`.
   - Open question: SPEC does not say whether these are medium or low, or whether a header macro is macro or direct.
2. **c/13, 674 medium macro edges.** These are system-header function-like macros emitted as macro: `assert` 634, `va_end` 14, `va_start` 9, `va_arg` 8, `S_ISDIR`/`S_ISLNK`/`S_ISREG` 4, `SUCCEEDED` 2, `va_copy` 2, `CFSTR` 1.
   - Quoted construct: `assert(rval == &list.head);`.
   - Open question: the same c/13 question, macro (medium) or direct, for a macro whose `#define` is not in the scan. The tool answers it two different ways (`S_ISDIR` as medium macro, `CPU_SET` as low direct).
3. **40 edges: invoking an object-like macro whose replacement is a function or function-like macro name.** `#define ITT_STUB ITT_STUBV` followed by `ITT_STUB(ITTAPI, __itt_pt_region, pt_region_createA, (const char *name))` gives 38 edges, high, macro, callee `ITT_STUB`. `#define AWS_NTOH aws_ntoh32` with `dest_copy = AWS_NTOH(dest_copy);`, and likewise `BYTE_CURSOR_READ`, give 2 edges, low, direct.
   - Open question: is such an invocation a macro edge to the alias, an edge to the target it expands to (as the Lua/Zig alias rule does for functions), or a direct call? And at which tier?
4. **156 sites, recall only: function-like macros inside function heads and prototypes.** `CJSON_PUBLIC(cJSON *) cJSON_Parse(const char *value)` with `#define CJSON_PUBLIC(type) type` produces no edge.
   - Open question: SPEC says function heads are not calls, and also that function-like macro invocations are macro edges. It does not say which wins when the macro sits in a head.
