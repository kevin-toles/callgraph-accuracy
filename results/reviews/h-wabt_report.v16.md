## Systematic patterns (scripted census, `h-wabt_r16_census.py`; union = 299 edges)
Each pattern was hand-checked on several edges, as cited in the table above.
1. **W10, 74 edges.** A local bound to a scanned function with a concrete declared return type is left as a low guess. These are the wasm-c-api examples: `auto x = get_export_{table,memory,global}(…)` returns `wasm::Table*` and similar, and `call(…).i32()`/`.f32()` returns `wasm::Val`.
2. **W2, 67 edges.** `wasm_v8::f` is not resolved through `namespace wasm_v8 { using namespace v8::wasm; }`. The tool emits a medium `wasm_v8.f` instead of the scanned `v8.wasm.f` at high.
3. **W3, 51 edges.** Structs generated by macros in wasm-c.cc (`struct wasm_X_t : X {}`) do not inherit from their scanned base. Calls are named on the generated type (`wasm_externtype_t#kind`, `wasm_func_t#call` and others) at medium, instead of `wasm.X#m` at high. This applies the 2026-11-12 rule that "declarations the expansion makes" type receivers.
4. **W1, 29 edges.** Files that have both `using namespace wabt;` and `using namespace wabt::interp;` resolve `Module/Global/Table/Memory::New`, `FuncType{…}` and a `Memory*` field to `wabt::X` instead of `wabt::interp::X`. This gives medium IDs that do not exist, or the wrong high constructor.
5. **W5, 18 edges.** A macro invocation with no `;` (`WASM_IMPL_VEC_BASE(val, )`, `WASM_DEFINE_VEC_BASE(val, Val, vec, vec, )`) directly before a function definition causes two errors: the function head is emitted as a call, and the body's calls get the file as caller.
6. **W4, 12 edges.** Functions generated from a macro invocation with an empty argument (`hide_/release_/borrow_val_vec`, `wasm_val_vec_new_uninitialized`) are low instead of medium.
7. **W6, 10 edges.** Calls through a `std::function` field (`module_stream_factory_`, `finalizer_`, `callback_`, `on_error_`, `error_callback_`, `Option::callback`) or a function-pointer template parameter (`ReadFn`) are emitted as direct/low or method/medium, not callback/unknown.
8. **W14, 10 edges.** Not calls: functional casts `Uint(x)` to an integer alias (9 edges in literal.cc), and one `#define` line.
9. **W9, 8 edges.** Receivers typed by a written declaration are left low: anonymous-union members (`Token::opcode_`, `Token::type_`, `Instr::imm_v128`) and one typed local (`Opcode opcode`, wasm-stats.cc:101/115).
10. **W11, 8 edges.** A local typed by its written construction is left low: `auto store = own<StoreImpl>(…)`, `auto v = vec(…)` and `auto v2 = vec<Val>::make_uninitialized(…)`.
11. **W7, 6 edges.** The class-scope alias `SharedValidator::FuncType` is not expanded. This covers 2 constructors, plus 4 field-chain receivers (`type.results.empty()`) that are left low.
12. **W8, 6 edges.** Bare calls of members inherited from an external base (`BindingHash` → `std::unordered_multimap`: `find`, `end`, `size`, `begin`; `RefImpl` → `v8::Persistent`: `Get`) are bare low names, not `Type#m` medium method.
13. **W13, 3 edges.** In-class field initializers have the file as caller (open defect cpp/10).
14. **W12, 2 edges.** `RefImpl<Ref>`'s template parameter `Ref` is taken to be `wasm::Ref`.
15. **W15, 1 edge.** A function-local type alias is not expanded (open defect cpp/18).

## Spec gaps (`h-wabt_r16_gaps.py`; counted separately, not as wrong)
- **SG1, 17 edges.** Construction of a template type parameter: `list_.push_back(T(std::forward<Args>(args)...));` and `out_expr->reset(new T(var, loc));`. The tool emits `T` direct low (3) and `T#<init>` constructor low (14). Open question: what callee ID and call_type should a constructor call on an unconstrained type parameter have?
- **SG8, 116 edges.** Macro-generated members whose macro arguments include string literals: `WABT_FEATURE(exceptions, "exceptions", false, "...")` defines `exceptions_enabled()`. The tool emits these as `wabt.Features#*_enabled`, medium. Open question: the generated-functions ruling lists identifiers, numbers, empty arguments and lone declarators as literal arguments. Does a string literal count?
- **SG5, 65 edges.** A static data member declared by an X-macro is used as a receiver: `writer_->WritePutsSpace(Opcode::Call_Opcode.GetName());`, where opcode.h declares `static Opcode Name##_Opcode;`. The tool emits `.GetName`, low. Open question: does the 2026-11-12 clause that expansion declarations "type receivers as written declarations do" cover data members generated through `#include "opcode.def"`?
- **SG7, 4 high edges against ≈52 low.** A scanned C++ smart-pointer template (`RefPtr<T>`, whose `operator->` returns `T*`): `Instance::Instantiate(store->I, module->I->self(), …)` with `RefPtr<Object> I` is resolved to `wabt.interp.Object#self` high. Calls on `Table::Ptr`/`Instance::Ptr` (`RefPtr<…>`) receivers stay low. Open question: does the 2026-11-12 Rust reading ("a type that derefs to its own type parameter has an unknown pointee") apply to C++ class templates in the scan, or does the 2026-10-29 smart-pointer rule (which names the pointee) apply? Whichever reading is chosen, one side is inconsistent with it (C2).
- **SG4, ≈13 edges.** A receiver typed only by a cast: `return const_cast<Module*>(this)->GetTable(var);` (8 edges in ir.cc) and `auto t = static_cast<wasm_callback_env_t*>(env); t->callback(…)` (5 edges). The tool emits `.m`/`t.m`, low. Open question: is a `static_cast`/`reinterpret_cast`/`const_cast<T*>` expression a typed receiver? It is not a call, so "Typed call results" does not cover it.
- **SG2, 12 edges.** Unqualified calls that resolve only through argument-dependent lookup: `ReadBinaryInterp("<fuzzer>", text, options, &errors, &module);` in the fuzzers, and `ValidateModule(module, errors, options)` in emscripten-helpers.cc, both with no `using`. The tool emits a bare low name. Open question: must C++ name resolution model ADL?
- **SG3, 7 edges.** Calls in default arguments of declarations: `Result ParseVarOpt(Var* out_var, Var default_var = Var());` and `static auto make(own<Config>&& = Config::make()) -> own<Engine>;`. The caller is the file. Open question: who is the caller of a default-argument expression (the declared function, its call sites, or the file), and is it a call at all?
- **SG6, 1 edge.** A call inside a `#define` replacement list that is expanded by `#include "wabt/opcode.def"`: `PrefixCode(prefix, code)},` (opcode.cc:35). The tool emits caller `src/opcode`, `PrefixCode` low. Open question: where are calls written in a macro body that expands at an include site in a non-source file reported, and with which caller?

Obsolete files: none identified.
